# Play mode: design

Date: 2026-09-18. Status: approved by the owner on the go page
(https://claude.ai/artifact/EwMKYnop72rgFoSKb1ZhXR, `go/decision` = go, and "go" in chat) after the
proposal page (https://claude.ai/artifact/JwdtQZhR3TAdskyyKj3Yim). This document is the binding
version of both pages for the code. Where a page and this file disagree, this file wins.

## Goal

A second in-match brain, opt-in per instance, that reads a live video feed of the match through a
trained detector and steers with rules, while everything outside a match and the existing farm
mode inside a match stay byte-for-byte as they are.

## Layers, so nobody asks again

BlueStacks runs the game. adb is the cable into it: every tap, swipe, screenshot and launch, and
the scrcpy server itself, travel over adb. scrcpy is a small Android program adb pushes onto the
instance; it streams the screen back over the same connection and sends nothing in. The stream
replaces `adb screencap` inside a match only. Outside a match screencap stays, because the 13
templates were validated on screencap frames (H.264 compression shifts pixels, and `close_x` has a
0.006 margin) and because the encoder costs BlueStacks about 60 percent of one core for as long as
it runs. Pull request 1's live pass measures the template score drift between a screencap and a
stream frame of the same menu; a later pull request may switch the whole loop to the stream if the
drift is small.

## Measured facts the design rests on

Stream spike on Pie64, 2026-09-18 (scrcpy 4.1 server, raw H.264 into Python, control off): frames
1600 x 900 native, 30.0 fps received, 33 ms median gap (37 p95, 69 max), 2.2 ms per frame to a BGR
array, 4.3 Mbit/s, BlueStacks `HD-Player.exe` at 22 percent of one core idle and 81 percent while
streaming, host 16 percent across all cores. Encoder `OMX.google.h264.encoder` (software, inside the
guest). Decoder threading, measured on a synthetic 30 fps clip: PyAV's default frame threading holds
back 18 packets before the first frame (600 ms at 30 fps); a single-threaded decoder emits the first
frame after 3 packets at 1.2 ms median, 3.4 ms max per packet. Machine: RTX 4080 SUPER 16 GB, Ryzen 7
7800X3D, 31 GB RAM, Python 3.13.13, uv 0.12.5, PyAV 18.1.0.

Today's loop, from `docs/notes/2026-09-10-frame-capture-assessment.md`: `adb screencap` 172 ms
median, `states.classify` 365 to 371 ms, `LOOP_POLL_INTERVAL` 0.20 s. That note's verdict, keep
screencap, stands for every phase but playing.

Data on disk: 181 frames at 1600 x 900 (recorder session 20260916-223234, menus only), 50 event
captures at 1600 x 900, 267 frames at 800 x 450 (49 in-match). No full-size match frames exist.

## 1. Shape

The controller's phase machine (returning, at_menu, queuing, playing) is unchanged. The fork sits at
the top of the playing phase only:

- `plan.play` false (default): farm mode, today's code path, untouched.
- `plan.play` true: play mode. Stream (section 2), detector (section 3), rules policy (section 4),
  then the same joystick swipe and attack taps farm mode already sends.

Fallback rule: if the stream stops, the model is missing, the newest frame is older than 500 ms, or
the detector raises, the current match finishes in farm mode and the feed says so. Degrade, never
crash, never stop attacking. This is the rule `match_vision` and the bush code follow today.

Shadow rule: with `plan.play` true and the `shadow` setting true, the detector runs and its boxes are
logged while farm mode drives. A model may drive a session only after a shadow-mode live pass is in a
pull request body.

## 2. Stream capture (C1)

Package `brawlfarm/play/`. Package data `brawlfarm/play/scrcpy-server` (the scrcpy 4.1 server jar,
733706 bytes, sha256 starting `deacb991ed250971`, Apache-2.0; its license text ships next to it as
`brawlfarm/play/LICENSE.scrcpy`). Module `brawlfarm/play/stream.py` (transport and lifetime) and
`brawlfarm/play/h264.py` (decoding).

Behaviour:

- Push the jar to `/data/local/tmp/scrcpy-server.jar` over the configured adb binary and the
  instance's serial on every start (734 KB, well under a second).
- `adb forward tcp:<port> localabstract:scrcpy`, one free local port per stream, found by binding
  port 0 and releasing it.
- Start the server with `CLASSPATH=/data/local/tmp/scrcpy-server.jar app_process /
  com.genymobile.scrcpy.Server 4.1 tunnel_forward=true audio=false control=false
  video_codec=h264 max_fps=30 raw_stream=true log_level=warn`. Without `CLASSPATH` the program
  prints `Aborted` and exits (live pass, 2026-09-19).
- Connect to the forwarded port; adb accepts the connection before the server listens and closes it
  silently, so peek for the first byte and retry until a deadline of 8 s. If the server process
  exits first, its output tail is the error.
- Decode on a background thread with `av.CodecContext.create("h264", "r")` set to one thread, fed by
  `parse()` on raw socket reads. The PyAV file-object demuxer does not decode this stream; the
  parser path does. Frame threading is never enabled (see the measured 600 ms hold-back).
- Hold only the newest frame as a BGR `numpy.ndarray` of shape (900, 1600, 3) and its monotonic
  timestamp. `latest()` returns `(frame, age_seconds)` or `(None, None)`. A frame older than
  `STALE_AFTER = 0.5` s is reported as `(None, None)`.
- The encoder emits a frame only when the display changes. Measured 2026-09-19 on the static
  BlueStacks home screen: 10 frames at 100 ms (the encoder's repeats of the last frame), then
  nothing. A match never holds still, so the staleness rule is right inside a match; a static
  menu reads as stale by design, which is one more reason menus stay on screencap and a fact any
  later move of the whole loop onto the stream has to handle.
- Optional recording: when opened with a path, every byte read from the socket is also appended to
  that file, so a recording is the raw H.264 elementary stream, no re-encode, no container. It plays
  in ffmpeg, PyAV and VLC, and `ffmpeg -i match-1.h264 -c copy match-1.mp4` wraps it when a
  container is wanted.
- `stop()` closes the socket, kills the server process, removes the forward, closes the recording.
  Stopping twice is a no-op. Any error on the decode thread ends the stream and is exposed as
  `error` on the object; `latest()` then returns `(None, None)`.
- Never taps. `control=false` is fixed, not a parameter. The stream module imports nothing that can
  send input.

The play extra: `[project.optional-dependencies] play = ["av>=14"]` and
`play-gpu = ["av>=14", "onnxruntime-gpu[cuda,cudnn]>=1.21"]`, mirrored as dependency groups the way `desktop` is,
and `av>=14` also in the `dev` group so the decoder tests run in CI. `brawlfarm.play.available()`
answers whether `av` imports, without importing it at module import time. Nothing under
`brawlfarm/core/` imports PyAV at import time; `observer.py` imports `brawlfarm.play.matchrec`, which
imports the stream module only when it opens a recording.

## 3. Detector (C2)

Module `brawlfarm/play/detect.py`. Loads `%LOCALAPPDATA%\brawlfarm\models\play.onnx` and `play.json`
(class list, per-class thresholds, training set hash, model name, input size). CUDA execution
provider when `onnxruntime-gpu` is present, CPU otherwise; the chosen provider is logged once.
Returns boxes in 1600 x 900 frame coordinates with class and confidence. First classes: self, enemy,
teammate, power_cube, box, bush, and the menu anchors that keep breaking: showdown_card, skull_star,
team_up_panel, event_tab.

## 4. Rules policy (C3)

Module `brawlfarm/play/policy.py`, a pure function like `match_vision.bush_decision`. Input: boxes,
gas fractions, seconds into the match, ability readiness. Output: heading in radians, attack bool,
hide bool. Rule order: gas first; any enemy inside `ENEMY_RADIUS`, move away; a power cube with no
enemy inside `CUBE_SAFE_RADIUS`, collect; a box in reach, attack; after `LATE_AFTER` seconds, nearest
bush and hold. Radii and timings live in one constant block in `policy.py`, provisional until the
first live pass, and are calibration values under CONTRIBUTING.md.

## 5. Controller fork and fallback (C4)

`brawlfarm/core/controller.py` `phase_playing` branches at its top on the plan flag.
`brawlfarm/play/session.py` owns one `PlaySession` per match: it starts the stream when the match
starts, stops it on results, and holds the fallback state. Inputs play mode may send: the joystick
swipe from `MOVE_ORIGIN`, the attack point, the ability buttons. No other tap exists on this path.
Feed rows: `play_on` (fps, model name), `play_summary` once per match (cubes, hides, enemies
avoided, placement when readable), `play_fallback` (reason).

## 6. Plan flag and switch (C5)

`play: bool = False` on the plan model in `brawlfarm/api/plans.py` and `brawlfarm/core/farmplan.py`,
carried by the PUT and GET plan routes. In `brawlfarm/web/src/instance/FarmPlan.tsx` a third `Switch`
under Pick quest brawlers, shown in Ladder and Prestige, disabled when the server reports the play
extra missing. Label `Play the match`. Help: "Steers the brawler from a live video feed and a
trained detector: away from enemies, toward power cubes, into a bush late. Needs the play extra and a
model file; without them the instance farms the match as usual." Disabled help: "Install the play
extra to turn this on: uv tool install \"brawlfarm[play]\"."

## 7. Packaging (C6)

Extras as in section 2. `GET /api/health` gains `play_available: bool`. The model is never in the
wheel: copied into the models folder by the owner, or fetched from a GitHub release asset pinned by
sha256 in `play.json`. The install lines documented in README.md: `uv tool install "brawlfarm[play]"`
and `uv tool install "brawlfarm[play-gpu]"`.

## 8. Dataset kit (C7)

Under `tools/play/`: `ingest_youtube.py` (owner-supplied URL list, yt-dlp at 1080p, frames at 2 per
second, drop frames without a visible mobile HUD, dedupe by perceptual hash), `frames.py` (the same
extraction from Pie64 recordings and `match-N.h264` files), `prelabel.py` (template matches written
as boxes for the menu anchors), a Label Studio project file with the class list, `train.py` (RF-DETR
nano on a COCO folder, held-out split by source video), `export.py` (ONNX plus `play.json` with
thresholds from the held-out precision curve), `score.py` (the model over every 1600 x 900 frame on
disk against template verdicts and recorder labels; zero never-tap false positives is the bar), and
`docs/play-training.md`.

## 9. Safety rails (C8)

CONTRIBUTING.md gains, in pull request 1: the play stream never sends input, scrcpy control stays
off. In pull request 4: play mode inputs are limited to the farm set; boxes the model labels as shop,
gem, upgrade, reroll or queue-exit controls are refused in the controller wherever they sit;
`play.onnx` and `play.json` are calibration artifacts and change only in a calibration pull request
with the training set hash, the score report and the held-out numbers; a model drives only after a
shadow-mode live pass.

## 10. Match recorder and HUD reader (C9, C10)

Recorder, pull request 1: in observe mode, while the frame recorder has a session open, each match
the classifier sees is recorded as `match-N.h264` in that session folder next to the frames and
`labels.jsonl`. `brawlfarm/play/matchrec.py` `MatchRecorder` opens a recording stream when the state
becomes IN_MATCH and stops it on RESULTS, TROPHY_SCREEN, MENU, MATCHMAKING or DISCONNECT, when the
session closes, or after 360 s. UNKNOWN and POPUP frames inside a match keep the recording open.
When the play extra is missing nothing is recorded and one line is logged. A stream error stops the
recording and disables match recording for the rest of that session, logged once. Farm sessions get
their match recording with the play session in pull request 6. The recorder's size caps count the
`.h264` files like any other session file; nothing is deleted.

HUD reader (`tools/play/hud.py`, `tools/play/actions.py`): a small detector for joystick base,
joystick knob, attack, super and gadget buttons; per frame the move vector is knob minus base
normalised by base radius, attack is the pressed state plus the aim-stick offset; writes
`actions.jsonl` next to the frames. Mobile recordings only, Showdown only, clean HUD; failing clips
are dropped with a count in the report. The cloned policy trained on those actions is release
1.3.0 and its own proposal.

## Build order

1. Stream module, match recorder in observe mode, extras, health key, adb helpers, the live pass
   tool (sections 2, 7 health key, 9 first line, 10 recorder).
2. Dataset kit, YouTube ingest, pre-labels (section 8).
3. HUD reader (section 10).
4. First model, as a calibration pull request (sections 3 data, 9).
5. Detector module and shadow mode (sections 3, 5 shadow half).
6. Policy, plan flag, switch, fallback, farm-session match recording (sections 4, 5, 6).
7. Release 1.2.0.

Each step is a branch off main, reviewed on sonnet per the project CLAUDE.md, with the gate and the
live pass named on the go page. Pull request 1's proof: a 60 s stream on Pie64 in the body with fps,
gap p95 and BlueStacks CPU; the template score drift between a screencap and a stream frame of the
same menu; one recorded match `.h264`; both extras install into fresh venvs; the CUDA provider
reported on this machine.

## Out of scope

Reinforcement learning. Replacing templates or OCR outside a match. Any tap play mode does not
already share with farm mode. The cloned policy (release 1.3.0).
